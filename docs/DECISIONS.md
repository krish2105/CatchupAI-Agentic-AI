## 2026-11-03: Build session M1

## 2026-11-03: Build session M2
- **ADR-017** Passwordless auth: 6-digit email code (primary, works across devices) plus magic link via `/auth/confirm` (token_hash). No passwords, no demo bypass. Sign-out uses local scope.
- **ADR-018** Tenancy enforced in the schema: every child row carries `owner_id` and references its parent by composite `(id, owner_id)` FK; RLS is `owner_id = auth.uid()`; `authenticated` receives column-level INSERT/UPDATE grants only. `document.storage_path` is a generated column, and storage INSERT requires a matching pending document row.
- **ADR-019** Server-written tables (chunks, agent runs, proposals, plans, tasks, quizzes) are SELECT-only for students. Writes go through the `server-only` admin client after ownership checks, or SECURITY DEFINER RPCs that re-check `auth.uid()` (approval, rate limit). This supersedes the plan note about invoker RPCs for agent runs.
- **ADR-020** Rate limits are per-student fixed windows in Postgres (`consume_rate_limit`), so they hold across serverless instances.
- **ADR-021** Times are stored as UTC instants; entry/display use the profile's IANA zone via `@date-fns/tz` (DST-safe, unit tested).

## 2026-11-03: Build session M3
- **ADR-022** Upload = (1) API registers the document row (quota, validation), (2) browser uploads straight to the private bucket at the DB-generated path (storage policy requires a matching pending row), (3) API processes synchronously (≤50 pages, `maxDuration` 60s). No file bytes pass through Route Handler bodies.
- **ADR-023** Chunks never cross page boundaries, so each citation names exactly one page. ~2,400-char windows with 300-char overlap.
- **ADR-024** Hybrid retrieval with RRF; lexical OR-query works without any AI key, vectors are added when embeddings exist. A passage only counts as evidence above `EVIDENCE_THRESHOLD` (lexical rank ≥ 0.08 or cosine ≥ 0.30); otherwise the system abstains ("I couldn't verify that…"). Thresholds should be re-tuned once real OpenAI embeddings are available.
- **ADR-025** Evidence search returns verbatim passages only (no generated text); generated answers come from the agent (M5) and must cite these passages.
- **ADR-026** pdf.js via `unpdf` (serverless build), font loading disabled; extracted text is treated as untrusted data everywhere.

## 2026-11-03: Build session M4
- **ADR-027** Planner = pure deterministic engine (no AI, no clock reads). EDF over per-day local windows; with all work released now, EDF is optimal for deadlines, so a reported shortfall is real under the block rules.
- **ADR-028** Scenarios are nested item sets: essential (required + 1 recommended), balanced (+ all recommended), full (+ optional). Recommended items without AI are review sessions of indexed notes, pointed at the best-matching page found by retrieval for the related assignment.
- **ADR-029** Proposals are server-created from saved data only (what-ifs must be saved first), expire after 6 h, and only one is pending at a time. Approval is a SECURITY DEFINER RPC: row lock, idempotent result, DB-side staleness check (assignment/profile `updated_at` after proposal creation), infeasible refused, assignment deadlines re-checked; constraints enforce ownership and no overlap. Approving supersedes the previous active plan (unfinished tasks cancelled).
- **ADR-030** Overdue required work is never silently scheduled; it is surfaced with guidance.

## 2026-11-03: Build session M5
- **ADR-031** One `LearningRecoveryAgent` (Agents SDK `Runner`, custom tracing disabled). Tools receive a server-built `AgentContext` (verified user id, user-scoped client, admin client only inside the draft path); the model never supplies identity.
- **ADR-032** The timeline comes from events recorded inside our tool wrappers (status completed/denied/failed, duration, privacy-safe args), streamed via SSE and persisted in `agent_runs`; it cannot show a call that did not execute.
- **ADR-033** Answers use a structured output separating `facts` (each course-material fact must cite source ids retrieved in this run) from `suggestions`; facts citing unknown ids are removed and counted. Retrieved text is passed inside `<source>` tags labelled untrusted.
- **ADR-034** `draft_recovery_plan` delegates all numbers to the deterministic planner and creates a pending proposal; agent study items need retrieved evidence and rank ahead of generic review items. A failed run expires its draft.
- **ADR-035** Tests replace only the LLM with a `ScriptedModel` speaking the SDK protocol. Browser E2E can use it only when `CATCHUP_TEST_MODEL=scripted` AND Supabase is local; the UI labels it "Scripted test model · not AI". Never available in deployments.
- **ADR-036** E2E now runs against a production build on :3100, so every E2E run also verifies `next build`.

## 2026-11-03: Build session M6
- **ADR-037** Knowledge checks use a deterministic cloze generator over the student's own indexed sentences (key concept = recurring course term; distractors = other course terms; seeded shuffle). Grounded, testable and available without an AI key. LLM-generated questions are a later option once a key is configured.
- **ADR-038** Answer keys live in `quiz_keys` (RLS on, no student grants); the browser only ever receives prompts/options/evidence. Grading and attempt writes happen server-side.
- **ADR-039** Insights only aggregate persisted rows (completed task timestamps set by DB trigger, graded attempts). Chart colours validated with the dataviz checker; single series → no legend; hover tooltip and a table view for accessibility.

## 2026-11-03: Practice, demo access, evaluation
- **ADR-046** (superseded by ADR-070) Spaced revision is a deterministic Leitner schedule over server-graded answers (miss → 1 day; correct → 3, 7, 14). Concepts never missed are not scheduled. Adaptive retests blank exactly the missed concepts.
- **ADR-047** One-click demo = Supabase anonymous sign-in + server seed through the visitor's own RLS client (admin only inside ingestion). Protected by Turnstile when configured (Supabase verifies the token for all sign-in methods), deleted after 24 h by a CRON_SECRET-protected job.
- **ADR-048** Evaluation runs the real system (local Supabase + deterministic engine). Cases needing an LLM are reported as skipped, never simulated. Retrieval evidence now includes query-term coverage after the eval exposed rank-only false abstentions.

## 2026-11-04: Replanning and Teach-It-Back
- **ADR-049** Replans subtract completed study-block minutes per assignment (from any plan, including superseded ones) so approved replans never reschedule finished work; missed blocks are surfaced, never auto-moved.
- **ADR-050** Teach-It-Back is deterministic: key concepts are recurring terms in the body sentences of evidence-filtered passages; feedback names covered/missing concepts with page citations and abstains without evidence. Attempts are server-written (students can read/delete only) so coverage can't be forged. An LLM may later phrase feedback but never decides coverage.
- **ADR-051** Rubric Decoder is deterministic and read-only until the student saves: sentences of an indexed brief are classified (weighted criterion > dated deadline > deliverable > requirement) with their page. Checklist rows are student-owned (RLS + composite keys to their own assignment and document); only `done` and `text` are updatable, so weights and kinds keep their source meaning.
- **ADR-052** Security baseline: nonce-based CSP from `src/proxy.ts` (all pages render per request), Origin check on writes on top of SameSite=Lax, HSTS. Demo accounts get separate, smaller budgets for costly operations; `consume_rate_limit` accepts only allowlisted buckets with fixed windows. CI runs unit + build + prod audit + bundle key scan, then integration/E2E/eval on a local Supabase.

## 2026-11-04: Feature batch
- **ADR-053** Calendar feeds use a 256-bit random token in the URL (calendar apps can't sign in); only its SHA-256 is stored, the link is shown once, revocation is immediate, and the feed query always filters by the resolved owner.
- **ADR-054** Trust drawer reads only server records (proposal, run events, citations) and states limits explicitly; it never summarises with AI.
- **ADR-055** Weekly next steps and the learning-trail study order are deterministic; prerequisites exist only when the student adds them (no inferred links), and loops are refused server-side.

## 2026-11-04: Batch A (path to 100)
- **ADR-056** Model fallback chain: one retry on a second model (`GEMINI_FALLBACK_MODEL`, which has its own free daily quota; ignored if it equals the primary) only for failures a second model can fix: daily quota, rate limit, 5xx overload, provider timeout, or the primary attempt's 100 s budget. Never for bad output, loops, cancellation or the overall 170 s timeout. The fallback restarts the conversation (no cross-model thought signatures). The first attempt's tool calls stay in the trace with `attempt` markers because they really ran; its draft is expired first so at most one draft per run is actionable; per-request search budgets count per attempt, the memory-suggestion budget per run. `agent_runs.model` names the model that produced the outcome; `fallback_from`/`fallback_reason` (migration 0016, check-constrained, server-written) say what was skipped and why. Tokens of a failed first attempt are now recorded too (ADR-074).
- **ADR-057** Streamed answers without showing unchecked claims: the answer is structured JSON, so the server parses it incrementally (`partial-answer.ts`, a stack scanner that only closes containers at valid cut points) and emits `answer` events. A fact is emitted only when its object is complete and it passes `verifyAnswer` on its own, so the claim check runs before display, not after. Suggestions (advice) stream every ~12 characters or when a suggestion finishes. Each model turn resets the live view; a fallback sends a reset too. The persisted, fully verified answer in `final` always replaces the live view, so streaming can't change what is stored. Gemini's streamed tool calls arrive in pieces, so `geminiFetch` reassembles them from the SSE bytes (passed through untouched) to keep Gemini 3 thought signatures working. `AGENT_STREAMING=off` is the switch if a provider's stream misbehaves.
- **ADR-058** Tool-result cache: in-process, per student, 60 s, 500 entries, for the three read tools only. Invalidation hooks the one place every authenticated write passes: `route()` opens an AsyncLocalStorage scope with the HTTP method and `requireApiUser()` clears the student's entries on any non-GET, again in `finally` (covers failed and partial writes). A per-student generation in the key drops reads that raced a write. The ownership check (`assertCourse`) is never cached. Chosen over a shared cache (Redis/DB) because it adds no service or cost; the price is up to 60 s staleness across server instances, accepted because the copilot only drafts and the planner re-reads everything when a draft is created and approved.
- **ADR-059** Plan self-check is a separate, pure re-check of the stored draft, not a flag from the planner: it trusts only the blocks and recomputes overlaps, block lengths, per-item deadlines (study items too, which the database's assignment-deadline guard doesn't cover), minute totals and required coverage. It is computed on every read (never stored, so it can't drift from the payload) and the payload itself never goes to the browser in run listings, only the result. "fail" blocks approval in the service before the RPC; "shortfall" is allowed to exist but approval is still refused by the existing infeasible rule, and the badge says exactly what doesn't fit and why.
- **ADR-060** Recovery score and clock skew: database timestamps (`completed_at`, set by trigger) and the rendering server's clock are different clocks. "Due by now" uses the server's `now`; "completed by" uses the end of the local day, so a completion stamped a few ms ahead is never lost.
- **ADR-061** Trace viewer `/runs/[id]` is a server component that reads `agent_runs` only through the signed-in student's client, so RLS is the access check (no separate owner logic to get wrong); a missing or foreign run is indistinguishable (not-found, no data). It shows only what was recorded during the run (ADR-032): tool order, stored argument summaries, outcomes and timings, run-level tokens and cited pages, plus an explicit "what this can't show" list (no model reasoning, no per-step tokens, shortened arguments). Known limit: once the app layout has streamed, Next.js serves the not-found UI with HTTP 200.
- **ADR-062** Self-hosted error tracking instead of Sentry (no third-party account, no data leaving our stack). One table of groups, not raw events: a fingerprint of source + normalised path + error name + redacted message with numbers folded, so ids, emails and counters don't split groups. Text is redacted before it reaches the database, never after. Only the service role can read or write; capture is best effort with a 1.5 s cap and never throws. Browser reports need a signed-in student (to throttle) but store no user id. Alerting reuses the uptime pattern: a scheduled GitHub Actions job that fails, so GitHub's own failure email is the page; a group is reported once, and again only if it comes back after being resolved.
- **ADR-063** Operator access by an env allowlist of exact emails (`OPS_OWNER_EMAILS`), not a database role: one owner, no migration, can't be granted from inside the app, and anonymous demo users are excluded. Non-owners get not-found on the page and 404 on the APIs, so the page's existence isn't revealed. The page reads with the service role only after the check. Uptime history comes from the public GitHub Actions API (no token, 3 s timeout, shown as unavailable on failure) instead of storing check results. The kill switch is tested at the service level, not in E2E, because pausing AI would leak into parallel copilot tests.
- **ADR-064** Public status page computes its state on each request from the same readiness check the uptime monitor uses, so the page and the alerting can't disagree. History comes from the Uptime workflow's own runs on GitHub (public API, best effort) rather than a second store. Incident notes are a typed list in the repository, updated by commit: only documented incidents, each with impact, cause and fix, so nothing is written on the fly.
- **ADR-065** In-app month calendar and recovery tracker, from the research report. Calendar: custom (no library: date-fns/Intl already present, ~0 KB added, full control over axe and theming; FullCalendar v7 only if drag or time grids are ever needed). Native `<table>` with one button per day rather than an ARIA grid with many interactive chips; roving tabindex for arrow keys; status as glyph + text; the selected day's items as a list. Nothing is draggable: deadlines belong to the course and plan changes go through the lab and approval, unlike Motion/Reclaim which reshuffle silently. Tracker: per-assignment progress towards one goal (goal-gradient; progress monitoring d≈0.40) instead of one backlog percentage; states come only from completed and scheduled minutes against the deadline; each state links to its next step (replan, plan, schedule). No consecutive-day streaks, points or leaderboards: a broken streak lowers persistence below having none, and these students are already behind. Week figures reset every Monday (fresh start).
- **ADR-066** Opposite-word rule in the claim check (Batch B). A claim that swaps "half" for "double" keeps almost every content word, so coverage accepts it (C20). The check now holds 18 curated pairs of word forms (`OPPOSITES`) and rejects a claim that uses one side where the passage sentence it most resembles uses only the other. Curated list instead of a thesaurus or a model: deterministic, no quota, each pair reviewable, and it fails closed only on exact word forms. Compared against the best-matching sentence (most shared content stems), not the whole passage, because one page often says "identical" about mitosis and "different" about meiosis; a sentence that contains both words of a pair never counts. Known limit: swaps outside the list still pass; the AI faithfulness judge (next in Batch B) is meant to cover those.
- **ADR-067** AI faithfulness judge as an opt-in second check (`FAITHFULNESS_JUDGE=on`), not a replacement for the word check. Order: word check first, judge second, and the judge can only remove facts, so a judge outage, timeout or prompt injection that makes it say "supported" can never let in a fact the deterministic check rejected. One batched request per answer (all cited facts together) because the free tier allows about 20 requests a day per model; verdicts cached by model + claim + passage hash. Off by default for the same quota reason and because the extra request adds latency; turned on after its agreement with the labels is measured (`evals/judge.eval.ts`). While it is on, facts are not streamed early, keeping the rule that an unsupported fact is never shown.
- **ADR-068** Calendar and tracker follow-ups from the research report. (1) "Done" view: the existing month calendar with `mode="done"` on Insights rather than a separate heatmap, so there is one calendar to learn. Shading uses fixed steps (0, <30, <60, <120, 120+ minutes), not relative to the student's best day, so a quiet week doesn't make small days look large; the minutes are printed in every cell and a table view lists them, so colour is never the only cue. Minutes come from completed blocks on their scheduled day. (2) Draft blocks: the pending, unexpired proposal's blocks are drawn dotted with "Draft, not approved" and a link to `/recovery?proposal=…`; nothing on the calendar can accept them, keeping approval in one dialog. (3) Course colours: colour = course (6 slots, both themes checked for contrast), icon = status; the course name always sits next to the swatch. (4) Forced colours: borders and a Highlight outline for the selected day, swatches keep their colour with a CanvasText border. (5) axe now runs with `wcag22aa` (target size) in the shell and ops tests; it found that the Insights charts put `aria-label` on role-less SVG groups (fixed: the chart is a group, each bar an image). (6) "X of the last 7 days" is optional and off by default (a per-browser choice in local storage), counts days with a completed block, builds 2 rest days into the aim of 5 and has no consecutive-day count, consistent with ADR-065.
- **ADR-069** LMS import from export files, not LMS APIs. Canvas, Moodle and Google Classroom all let a student download a calendar (.ics), and Canvas/Common Cartridge give a course package (.imscc); an API integration would need per-institution OAuth apps and admin approval. The file is parsed in the browser (`src/lib/import/lms.ts`: ICS with line folding, TZID, all-day dates; RFC 4180 CSV; a minimal ZIP reader using `DecompressionStream`, capped at 20 MB per file and 5 MB per entry against zip bombs), so nothing leaves the device until the student confirms. Every assumption is shown on its row (no time zone → student's zone; no time → 23:59; ambiguous D/M; Canvas `due_at` read as UTC). Saving goes through one batch endpoint (`/api/import/assignments`, ≤200 items, one rate-limit unit) with the student's own client, so RLS applies; courses are matched by name case-insensitively and an item with the same course, title and due time is skipped, so re-importing is safe. Estimates reuse the syllabus import's rules.
- **ADR-070** Spaced revision moves from the Leitner boxes (1/3/7/14 days) to FSRS (`ts-fsrs` 5.4.2, pinned, no dependencies, default FSRS-5 weights, 90% target recall). The schedule is still derived, not stored: every graded answer is replayed per concept (miss = Again, correct = Good), so no migration is needed, deleting an attempt changes the schedule consistently, and the month calendar's revision marks pick it up unchanged. Fuzz and same-day learning steps are off so dates are deterministic and whole days. Policy unchanged: a concept never missed isn't scheduled. Example from the unit replay: miss → 1 day, then 3, 8, 22, 54, 124 days after successive correct answers. Per-student weight optimisation is left out until there is enough real review history to fit.
- **ADR-071** Pre/post learning gain per catch-up pack without a new table. A pack's graded check is an ordinary server-graded quiz built only from that document (`documentId` on `/api/quizzes/generate`; the document must belong to the course and to the student, else 404), labelled with the fixed topic "Catch-up: <file name>". The existing per-topic first-vs-latest comparison then gives before (first attempt) and after (latest), so no migration and nothing new to secure; Insights lists a pack only once it has both. Limits: "before" means the first attempt, even if the student took it after studying; questions are drawn fresh each time from the same document, so before and after are comparable in scope, not identical items; renaming a document starts a new series.
- **ADR-072** Organisations and memberships (migration 0018). Roles student/teacher/admin on a membership, not on the account, so one person can teach one class and study in another. Teachers get aggregates, never records: the students' own tables keep owner-only RLS unchanged, and staff read only through SECURITY DEFINER functions that check the caller's role (`org_members`: name, role, sharing flag; `org_class_summary`: counts and an average). Totals count only students who opted in (`share_progress`, off by default, withdrawable at once) and are hidden below 3 of them, so a single student's numbers can't be read off a total. Joining is by a 10-character code (32^10 space, write rate limit on the endpoint); only staff can read it, through a function, since the column has no grant. All writes are functions (create, join, role, share, leave); there are no INSERT/UPDATE grants. The last admin can't step down or leave while others remain. Demo accounts are refused. Not built yet: code rotation, per-course classes inside an organisation, teacher-assigned work.
- **ADR-073** Activation is measured, not assumed. The milestone is the first finished study block of an approved plan: the moment a student is recovering on a schedule they chose. Mission Control shows a 7-step checklist in the order that reaches it fastest (course → deadline → notes → copilot → approve plan → finish a block → knowledge check), each step read from the student's own rows, hidden once all are done. The owner's `/ops` shows the funnel for full accounts created in the last 30 days (demo accounts excluded): accounts per step, activation rate, and median time from sign-up to the first approved plan (time to value). It is derived from existing tables with the service role after the owner check: no analytics scripts, events or third-party trackers, consistent with the privacy notice. Benchmarks from the research are generic SaaS figures (median checklist completion about 10–19%), not edtech; real numbers come with the pilot.
- **ADR-066** Billing wiring keeps every trust decision where it already was: the database decides who is an admin (`org_billing` raises for anyone else), billing ids are read only with the service role, and the plan changes only from a webhook whose HMAC over the raw body verifies, applied once and in order by `apply_org_subscription`. Verified events always get 200 (applied or ignored) so Stripe stops retrying; anything unverified gets 400. Checkout puts the organisation id in the subscription metadata so the webhook can't be pointed at another organisation. The /pricing page never states a price the owner hasn't set. Plan limits raise only the daily copilot limit for Class members (2×), never a demo account's, using the allowlisted window.
- **ADR-067** Invitations store no email address: the database keeps a sha-256 of the lower-cased address (to match the invitee's verified JWT email at acceptance) and a masked hint for the admin, plus only the hash of a 24-byte random token. The token is returned once to the server, which emails it when SMTP is configured and always shows it to the admin once. Acceptance re-checks expiry, revocation, seats and the email match inside one locked transaction. Admin destructive actions live in the database too: remove member, rename and delete (exact-name confirmation, refused while a paid plan is active) are audited; deleting an organisation never touches students' own study data.
- **ADR-074** Every model call in a run counts towards its tokens, including turns of an attempt that later failed (they were billed). Each attempt runs with its own `RunContext`, whose usage the Agents SDK adds to after each model response, so it is still readable after the attempt throws. The run stores the sum of all attempts plus the judge, completed or failed, and the daily token budget (which sums all runs) sees it. A model call that itself fails (for example a 429) returns no usage and adds nothing. The optional "X of the last 7 days" view (ADR-068) was already built and needed no change.
- **ADR-075** Scanned PDFs are read with OCR by the Gemini model the app already uses, instead of a bundled OCR engine (Tesseract would add tens of MB of language data and slow serverless functions, and reads slides and maths worse). Only after normal extraction finds no text: duplicate check first, then the kill switches and daily token budget, then one of the student's daily copilot requests, then a single request with the PDF inline (scans up to 20 pages, 90 s). The prompt says to transcribe only and never follow instructions in the file; the output is JSON per page, normalised and capped, and then goes through the same chunking, retrieval, citation and injection checks as extracted text. Documents store `text_source = 'ocr'`, the model and its tokens (migration 0021); the daily budget sums them with agent runs, including OCR calls that produced no usable text. The course page labels OCR documents "from scan" and asks the student to check numbers and formulas against the original. Before 0021 is applied, the code behaves exactly as before (no OCR). Off with `PDF_OCR=off`; never called in local automated tests.
- **ADR-076** Streamed Gemini tool calls: the thought signature is saved as soon as its chunk arrives, not when the stream closes (the SDK can send the next request first), and tool-call pieces without an `index` (Google omits it) are grouped by id, so parallel calls are kept apart. - **ADR-078** A refused draft says how to recover instead of only refusing. It lists the source ids actually retrieved (none, if the search found nothing) and says to retry with `studyItems: []`, because the planner still schedules every assignment. After two refused drafts in an attempt, further drafts are denied and the model is told to answer the student. - **ADR-079** A fact with no source id must be grounded in this run's tool results. Before, `verifyAnswer` kept every fact that cited nothing, on the assumption that such facts came from tools (deadlines, availability). So any statement, including uncited course content, could skip the citation check by citing nothing. The live S2 trace on 7 Nov showed three kept facts without sources (all correct tool facts), which exposed the gap. Now the data tools (preferences, assignments, progress, the drafted plan, memory) record their results in the run context, and `toolFactSupport` keeps an uncited fact only if a data tool answered, every number in it appears in those results (also as hours, the student's local time or an item count), and at least 60% of its content words, apart from common scheduling words, appear there too. Otherwise it is removed and counted like any unsupported fact, both in the final answer and in the live stream. Deterministic, with no extra model call. Limitation: like the passage check, it confirms the pieces are in the data, not that the sentence combines them correctly.

## 2026-11-08: UAE study defaults (Y1)
- **ADR-081** Local calendar as opt-in planner rules (Friday prayer, prayer-time breaks, Ramadan, Hijri dates). (1) **Storage:** its own table `calendar_prefs` (migration 0022, the `notification_prefs` pattern: RLS, column grants, check constraints that mirror the API schema) rather than new `profiles` columns, because `getProfile` selects explicit columns and every page would fail between a merge and the owner applying the migration. Reads return the defaults on `isMissingSchema`, the export skips the table and saving answers 503 `not_available`, so the code is safe to deploy first. (2) **Prayer times** come from `adhan` 4.4.6 (exact pin; MIT; no dependencies; published 31 Aug 2026; `npm audit --omit=dev` 0 vulnerabilities) for the student's chosen UAE city (8 fixed city-centre coordinates, from Wikipedia) and method (UAE/Dubai or Umm al-Qura). They are computed on the server, not "on the device" as the task first said: the planner and the copilot's drafts run there, a copilot run has no browser, and the server could not verify windows sent by a browser. The app never asks the device for its location; only the city key and method are stored. Browser code imports `calendar-options.ts` and `hijri.ts`, so `adhan` stays out of the client bundle. (3) **Breaks keep the student's minutes:** the day's window pauses for a break and resumes after it; a gap shorter than a block (15 min) is skipped without spending minutes; a day never runs into the next study day's window. Friday 12:00–14:00 local; prayer breaks from 5 min before to 10 min after each of the five prayers; in Ramadan no study from an hour before Maghrib ("no heavy block" read as no block at all: the simplest rule to test) to 30 minutes after it, for iftar. The break is a before/after pair (`IFTAR_BREAK`, 60/30 min); the 30 minutes after Maghrib are the owner's decision in the PR #5 review (10 Nov 2026). Before that the break ended at Maghrib, so study resumed at the meal. Chosen over removing the break's minutes, which would turn a prayer break into a shortfall. (4) **Ramadan days:** month 9 of `Intl` `islamic-umalqura` on the student's local date, or the student's own start and end (at most 30 days, the longest Hijri month). Daily minutes × (100 − percent) / 100, rounded down to 5 (0–75%, default 25%), and an optional start time used on Ramadan days only, for late-evening study. (5) **The engine stays pure:** rules arrive precomputed in `availability.calendar` (absolute break intervals and Ramadan dates); without them the windows are exactly as before (tested against the old output in three time zones, and the 200 existing randomized runs are unchanged). (6) **Stale drafts:** a trigger stamps the server-only `rules_changed_at` only when a change affects planning (a rule switched on or off, the city or method while prayer breaks or Ramadan mode are on before or after, or the Ramadan details while Ramadan mode is on), and `approveProposal` refuses an older pending draft with the existing 409 `stale` before calling the unchanged `approve_proposal` RPC; toggling Hijri dates is display only and doesn't invalidate a draft. Rejected: redefining the SECURITY DEFINER RPC in 0022 to add one line. The gap between this check and the RPC is a few milliseconds of the same student's own requests. (8) **Hijri labels** use the built-in Umm al-Qura calendar, change at midnight rather than sunset and are labelled approximate (official UAE dates follow moon sighting); the labels carry `suppressHydrationWarning` because a browser's ICU may spell month names differently from Node's.
